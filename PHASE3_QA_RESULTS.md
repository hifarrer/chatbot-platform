# Phase 3 QA results — training on the new model tiers

Run date: 2026-09-03. Verified against the **live Render Postgres** and the **live Bunny zones**, with real OpenAI training runs on Luna (`gpt-5-mini`) and Terra (`gpt-4.1`).

**Result: 112/112 live end-to-end checks, 56/56 offline training checks, 38/38 offline storage checks.**

## Defects found and fixed

### 1. Multi-page PDF text was corrupted — `services/document_processor.py:108`

`text += page_text + "\\n"` — a literal backslash-n, where `HEAD` had `"\n"`. Every PDF page boundary put the two characters `\n` into the extracted text, hiding the paragraph break from the chunker and inlining the escape into the knowledge-base prompt and stored chunks. Introduced in this uncommitted diff. Fixed to a real newline.

### 2. Terra could not complete any training run — `services/model_catalog.py:49`

`training_max_tokens=4000` truncated the knowledge-base JSON mid-object and failed the run with `kb_invalid_json` (*"Unterminated string … char 16227"*). This was on a **12.8k-character corpus of five small documents** — not a large one. The earlier narrowing of Terra's *input* slice to 24k tokens had treated the symptom; the output budget was the binding constraint.

Raised to `16000`, matching Luna and Sol. `gpt-4.1` allows 32k output tokens, so this is still half the cap, and a run only bills for tokens it actually generates.

Terra now trains the same corpus in 41.8s and produces a *richer* knowledge base than Luna (26 facts / 49 QA patterns vs 20 / 24).

### 3. The vector index never reached the chat prompt — `services/chat_service_openai.py:230`

The most consequential finding, and silent. OWL-10's premise is that semantically retrieved source chunks make a fact buried in a long document answerable. Retrieval worked perfectly — `search_chunks` returned the correct passage every time, at sensible scores. The chunks were then discarded at the last step, because the distilled facts had already consumed the 4000-character budget:

| Question | Facts used | Left | Top chunk needs | Chunks in prompt |
|---|---|---|---|---|
| `NW-4471` | 3616 | 384 | 1710 | **0** |
| `PX-820` | 3589 | 411 | 2460 | **0** |
| tier 3 price | 3549 | 451 | 2845 | **0** |

Chunks are ~800 tokens (1200–2900 chars); the leftover was never more than 451. So the index was built, embedded, stored, cached and searched for nothing, and any fact that existed only in the source documents was unanswerable. Both tiers failed on `NW-4471` and `PX-820` for exactly this reason.

Fixed by raising the total budget to **12000 characters** and reserving **half for chunks** — the facts are capped only when there is an index competing for room. 3–4 source chunks now reach every prompt. `_merge_chunk_passages` also logs what it merged, because the failure mode is otherwise invisible.

**Cost note:** this raises prompt tokens per chat message (roughly 4000 → up to 12000 characters of context, about +2000 tokens). That draws against each plan's monthly token allowance, so high-traffic bots will consume quota faster than before.

### 4. Deleting a trained chatbot 500'd on Postgres — `app.py:615`

`token_usage.chatbot_id` holds an FK to `chatbot` with no cascade, and `delete_chatbot` purged `ChatbotUsage` and `TrainingRun` but never `TokenUsage`. Any customer who trained or chatted a bot and then deleted it got a 500, and the bot survived. `qa_phase4_app.py` missed this because SQLite does not enforce foreign keys by default — it only appears against the real database.

Added `detach_token_usage()` alongside the existing `purge_training_runs()`, wired into all three delete paths (user delete, admin delete, admin user-chatbot delete). It sets `chatbot_id = NULL` rather than deleting: the column is nullable, Postgres treats NULLs as distinct in the unique constraint, and this stops a customer zeroing their month's bill by deleting the bot that spent it.

## Caveats

- **The local venv is not Render.** Python 3.13 + Flask 3.1.2 + stripe 13 locally, against `requirements.txt` pins of `Flask<3.0.0` / `stripe<8.0.0` and a Render build on 3.11.9. A local pass is strong evidence, not proof.
- **Prod still runs the old code** against a database that already has the new columns. This pass did not change that; the deploy remains the step after the push.
- **Sol (`gpt-5`) was not tested** — excluded by choice to limit spend.
- **The multi-batch map-reduce path was not exercised live.** The 12.8k-char corpus fits inside one map call on both tiers. `qa_phase3.py --live` covers that case with its buried-`ZULU-774` handbook test.
- **`numpy` was missing from the local venv** despite being in `requirements.txt`; without it `services/embedding_service.py` degrades to pure-Python scoring (~100× slower per chat turn). Installed before testing. Worth confirming it is present on Render.
- **Chat 500s on a Windows console.** An emoji `print` in the chat route hits cp1252 and the route's handler turns it into an error response. Pre-existing (also in `HEAD`), harmless on Render's UTF-8 stdout, but it invalidated a whole run's chat assertions here. Run local tests with `PYTHONUTF8=1`.
- **A chatbot with a NULL `url_name` 500s the dashboard** (`dashboard.html:123` builds a URL from it). No production row is affected — every real chatbot has one, since the create route sets it — but rows inserted directly need it. Reported, not fixed.
